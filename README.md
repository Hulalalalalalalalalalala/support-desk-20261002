# 客服工单工作台

记录客户问题、指派处理人、添加处理备注，再以明确解决说明关闭工单。

## 运行

需要 Python 3.10 或更新版本，仅使用标准库，无依赖安装步骤。请在本目录运行：

```sh
python3 -m support_desk --root ./state demo
python3 -m unittest discover -s tests -v
```

这是本地命令行程序，不监听网络端口，无账户或密码。`demo` 在指定 root 的临时子目录中读取 examples 样例并演示业务，结束后清理样例状态，不改变现有数据。

## 正常使用

公开 API：`from support_desk import SupportDesk`，然后 `SupportDesk(root)`。每个命令接收可选的 JSON 文件，其对象键与 API 方法参数一致。例如：

```sh
python3 -m support_desk --root ./state open examples/tickets.json
```

JSON 数组会按顺序执行多个独立操作；先前成功操作保留，后续失败不会回滚整批。重跑登记命令遇到已存在的标识会报错。

- `open` → `SupportDesk.open_ticket(...)`：可选 `opened_at`，非负整数分钟；提供时工单同时带初值为 `null` 的 `first_response`，省略时不写这两个字段。参数名见 `core.py` 的公开方法签名。
- `get` → `SupportDesk.get(...)`。参数名见 `core.py` 的公开方法签名。
- `assign` → `SupportDesk.assign(...)`。参数名见 `core.py` 的公开方法签名。
- `transfer` → `SupportDesk.transfer_ticket(ticket_id, assignee, reason, transferred_at)`：将已指派的未结工单转交给另一位处理人。四个参数均必填：`ticket_id`、`assignee`、`reason` 去除首尾空白后须为非空字符串，标识按去空白后的值区分大小写查找，原因内部的空白与换行原样保留；`transferred_at` 只接受非负整数分钟（拒绝布尔值、浮点、字符串和 `null`）。只允许存在、状态为 `open` 且已有处理人的工单转交；目标处理人与当前处理人相同、工单不存在、已关闭或未指派均抛出 `ValueError`。`transferred_at` 不得早于工单已有 `opened_at`，也不得早于 `transfer_history` 末条转交时间，相等允许；无登记时间的旧工单不检查 `opened_at` 且不补写时间字段，非法时间抛出 `ValueError`。成功返回完整工单并按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后 `get` 及其他返回完整工单的入口仍读到相同结果：工单 `assignee` 更新为目标处理人，并在 `transfer_history` 数组末尾追加一条只含 `from_assignee`、`to_assignee`、`reason`、`transferred_at` 的记录，来源取操作前的实际处理人；旧工单缺少该字段时从空数组开始，且仅在首次成功转交时才新增该字段，记录按成功提交顺序保存。转交保留状态、分类、优先级、备注、解决说明、首次响应、后续答复与知识快照等既有字段，转交原因不加入备注或答复，也不参与既有内容搜索。工作量报告按转交后的当前归属统计，首次响应耗时与跟进等待仍按原时间计算；关闭与重开保留转交历史，重开后继续转交时仍须遵守时间顺序。既有 `assign` 等指派入口保持原行为，不补记历史，后续转交仍取当前归属。参数类型错误或文本参数全为空白、缺少必填参数或出现未知参数分别抛出 `ValueError` 与 `TypeError`；失败不改变数据、不留下转交记录、不创建目录或文件。
- `handover` → `SupportDesk.handover(source_assignee, assignees, reason, transferred_at, max_open=5)`：整组交接，把某处理人的全部未结工单一次分给指定接收人，全部成功或全部不变。`source_assignee`、`assignees`、`reason`、`transferred_at` 必填，`max_open` 默认为 5。来源、原因及接收人名称去除首尾空白后须为非空字符串，名称区分大小写，原因内部空白原样保留；`assignees` 仅接受非空数组，规范化后不能重名或包含来源；`transferred_at` 只接受非负整数分钟，`max_open` 只接受正整数，两者拒绝布尔值、浮点、字符串和 `null`。只选当前归属等于来源且状态为 `open` 的工单，按 `urgent`、`high`、`normal`、`low` 顺序分配（缺优先级按 `normal`），同级按登记时间升序、无登记时间排在后面，再按 `ticket_id` 区分大小写升序。接收人的起始负荷为其全部未结工单数，每次选择负荷低于 `max_open` 且最少的接收人，同负荷按名称区分大小写升序，随后负荷加一，候选输入顺序不影响结果。`transferred_at` 不得早于任何所选工单的 `opened_at` 或 `transfer_history` 末条转交时间，相等允许；缺登记时间的工单不检查也不补写。成功返回按分配顺序排列的完整工单数组，逐单更新归属并按 `transfer` 的格式在 `transfer_history` 末尾追加记录，来源取原归属，目标取分配结果，原因与时间取共同输入；缺历史时仅在成功时才新增该字段。结果按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后一致。交接保留分类、优先级、答复及知识快照等其他字段，不追加备注，不刷新响应或跟进等待；工作量报告按新归属统计。输入非法、容量不足以接收全部所选工单或任一交接时间倒退均抛出 `ValueError`，缺少必填参数或未知参数抛出 `TypeError`；这些拒绝不写文件、不创建目录或文件，不留下部分归属或历史变化。合法输入没有所选工单时返回 `[]`，不创建目录或文件。既有转交、指派、自动指派及其他入口保持原行为。
- `route-assign` → `SupportDesk.route_assign(rules, max_open=5, strategy="greedy", assignee_limits=None)`：按分类把未指派工单分派给各类别规则内的处理人。`rules` 必填，仅接受非空数组，每项为只含 `category`、`assignees` 两个键的对象，缺键或多键均抛出 `ValueError`。`category` 为 `null`（Python `None`）或去除首尾空白后非空的字符串，内部空白原样保留、比较区分大小写，`null` 规则只匹配未分类工单；规则间规范化后的类别不许重复，同条规则内处理人去除首尾空白后须为非空字符串、区分大小写且不能重名，跨规则可以共用同一人名。`max_open` 默认为 5，只接受非布尔正整数（拒绝布尔值、浮点、字符串和 `null`）。`assignee_limits` 可选，省略、`null` 或空对象等同于所有人共用 `max_open`；传对象时按人设置本次分派的未结工单上限，键为处理人名称（去除首尾空白后区分大小写、内部空白原样保留，须出现在本次 `rules` 中），值为非负整数（拒绝布尔值、浮点、字符串、`null` 与负数）；未列出的人仍使用 `max_open`，上限为零或已有负荷达到、超过个人上限的人不接新单，上限对象的输入顺序不影响结果，上限仅本次生效、不保存。名称非字符串或全空白、规范化后重名、未知名称、非 `null` 的非对象参数均抛出 `ValueError`，即使没有候选或所有人都单独设限，全部参数也照常校验。`strategy` 省略或传原值字符串 `greedy` 时逐单分派：候选仅为状态为 `open` 且 `assignee` 缺失或为 `null` 的工单，按 `urgent`、`high`、`normal`、`low` 排序（缺优先级按 `normal`），同级按 `opened_at` 升序、无登记时间排在后面，再按 `ticket_id` 区分大小写升序；已有答复不影响候选资格。工单缺少 `category` 或为 `null` 视为未分类，每单只使用与其类别精确匹配的那条规则，未分类规则不会为已分类工单兜底，无匹配规则即跳过。处理人的起始负荷为其当前全部未结工单数（包含其他类别、已分配给该人的工单），同名人在各规则间共享同一负荷；每次在该单规则内选择负荷低于个人上限（`assignee_limits` 中的值，未列出时为 `max_open`）且最少的人，同负荷按人名区分大小写升序，分派成功后该人负荷加一；规则与处理人的输入顺序不影响结果。传原值字符串 `coverage` 时改为全局分派：在每张工单只交给其类别规则中一人、跨类别共享同一容量、新增分派不使任何人负荷超过其个人上限（已达或超过上限的人不接新单）、既有归属不调整的前提下，选择成功分派数最多的整体方案，容量不足或没有匹配规则的工单留待分派而不报错；方案总数相同时，按候选顺序逐单比较是否分派，在首个不同位置选择分派该工单的方案；所选工单集合相同时，按候选顺序比较接收人名称序列，选择区分大小写字典序最小的方案。`strategy` 只接受 `greedy`、`coverage` 两个原值字符串，其他值（含布尔值、数字、`null`、其他字符串）均抛出 `ValueError`，无候选时也照常校验。无匹配规则或容量不足时跳过相应工单并继续，不中断、不报错。两种策略都返回只含 `assigned` 与 `remaining` 的对象：`assigned` 为成功分派的完整工单数组，`remaining` 为未分派工单的标识数组，两者均保持候选顺序。成功时只更新工单的 `assignee` 字段（不追加转交历史、备注或其他字段），有成功分派才按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后结果一致，其他工单字段与知识数据保留；策略与规则不保存。没有任何成功分派时不写数据、不创建目录或文件；无候选时两个数组均为空。规则类型或内容非法、`max_open`、`strategy` 或 `assignee_limits` 非法均抛出 `ValueError`，缺少 `rules` 或出现未知顶层参数抛出 `TypeError`；输入拒绝不写数据、不创建目录或文件。既有 `auto-assign`、分类、手动指派、转交、交接、队列、报告、知识入口与 `demo` 保持原行为，不自动触发 `coverage` 策略。
- `route-handover` → `SupportDesk.route_handover(source_assignee, rules, reason, transferred_at, max_open=5)`：按分类把某处理人的全部未结工单一次交接给各类别规则内的处理人，全部成功或全部不变。`source_assignee`、`rules`、`reason`、`transferred_at` 必填，`max_open` 默认为 5。来源与原因沿用 `handover` 的文本校验（去除首尾空白后须非空，原因内部空白原样保留）；`transferred_at` 只接受非布尔的非负整数分钟；`max_open` 只接受非布尔正整数。`rules` 的格式、分类匹配、文本规范化与上限校验沿用 `route-assign`：仅接受非空数组，每项为只含 `category`、`assignees` 两个键的对象，`category` 为 `null` 或去首尾空白后非空的字符串且规则间不重复，同条规则内处理人去空白后非空、区分大小写且不重名，跨规则可共用同一人名；此外任何规则的接收人都不得包含来源。即使没有待交接工单，也校验全部输入。只选当前归属等于来源且状态为 `open` 的工单，排序沿用 `handover`（`urgent`、`high`、`normal`、`low`，缺优先级按 `normal`，同级按登记时间升序、无登记时间排在后面，再按 `ticket_id` 区分大小写升序）。每单只匹配与其类别精确一致的那条规则，未分类规则不为其他类别兜底；接收人现有负荷为其全部未结工单数，跨规则共享同一容量，负荷已达或超过 `max_open` 的人不接新单。存在完整可行方案时交接全部工单；多解时按工单顺序比较接收人名称序列，取区分大小写字典序最小者，规则与人名的输入顺序不影响结果（例如甲类可交给 X、Y，乙类只可交给 X，两人均空闲且上限为 1，甲先排序时甲交给 Y、乙交给 X）。缺匹配规则或整体容量不足均抛出 `ValueError`，不允许部分交接。`transferred_at` 不得早于任一所选工单的 `opened_at` 或 `transfer_history` 末条转交时间，相等允许；缺登记时间的旧工单不检查也不补写，缺历史仅在成功时新增。成功按上述顺序返回完整工单数组，逐单更新归属并按 `transfer` 的格式在 `transfer_history` 末尾追加记录，来源取原归属，原因与时间取本次输入；结果按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后一致。其他工单字段与知识资料保留，工作量按新归属统计，响应与跟进等待不重置。非法参数或规则抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件、不留下部分变化。合法输入没有所选工单时返回 `[]`，不创建目录或文件。既有 `handover`、`route-assign` 及其他公开入口与 `demo` 保持原行为。
- `note` → `SupportDesk.note(...)`。参数名见 `core.py` 的公开方法签名。
- `close` → `SupportDesk.close(ticket_id, resolution, closed_at=None)`：关闭已指派工单。`closed_at` 可省略或为 `null`，此时保持原结果、不新增字段；提供时只接受非负整数分钟（拒绝布尔值、浮点、字符串与负数），且不得早于工单已有的登记时间、首次响应、任一后续答复、客户追问、转交时间或重开历史中的结案时间（相等允许），否则抛出 `ValueError`。合法时将该时间作为 `closed_at` 随完整工单保存并返回。
- `close-many` → `SupportDesk.close_many(items)`：一次关闭明确选定的一组工单，组内全部成功或全部不变。`items` 必填，只接受非空数组；每项为只含必填 `ticket_id`、`resolution` 与可选 `closed_at` 的对象，缺键、多键或非对象均抛出 `ValueError`。`ticket_id` 与 `resolution` 均须为去除首尾空白后非空的字符串，标识按去空白后的值区分大小写查找，解决说明内部的空白与换行原样保留；`closed_at` 省略或为 `null` 时不新增结案时间，提供时只接受非布尔的非负整数分钟，拒绝浮点、字符串与负数。规范化后重复的工单标识拒绝整批。所选工单均须存在、状态为 `open` 且已指派，不要求首次响应或登记时间；每个结案时间不得早于该工单已有的登记时间、首次响应、任一后续答复、客户追问、转交时间或重开历史中的结案时间（相等允许）；旧数据缺少的历史按无记录处理，不补写字段。成功时按输入顺序返回完整工单数组：每张工单状态改为 `closed`，解决说明替换为本次值，提供的时间作为 `closed_at` 保存，沿用现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后一致。其他工单字段、处理历史、知识快照与知识资料保留；结案工单退出未结队列，结案报告、重开和知识发布采用原规则。任一项结构、文本、重复标识、时间或工单条件非法均抛出 `ValueError`，缺少顶层 `items` 或出现未知顶层参数抛出 `TypeError`；校验失败不写数据、不创建目录或文件，也不留下部分结案（例如末项未指派时，前面合法工单仍保持未结）。命令沿用 JSON 参数对象；接收外层数组时每个对象仍是独立批次，前一批成功不因后一批失败回滚。既有 `close`、其他公开入口与 `demo` 保持原行为。
- `closure-report` → `SupportDesk.closure_report(as_of)`：统计当前 `closed` 工单的结案耗时，重开历史不重复计为结案。`as_of` 为必填的非负整数分钟；任一当前关闭工单的登记或结案时间晚于 `as_of` 时整个查询抛出 `ValueError`，未关闭工单与历史时间不参与检查。返回只含 `as_of`、`total`、`timed`、`untimed`、`average_minutes`、`max_minutes`：有效耗时为 `closed_at` 减原 `opened_at`，缺任一时间的工单计入 `untimed` 且不参与耗时计算；无有效样本时两项耗时为 `null`，无数据时三项计数为零。只读，不写数据、不创建目录或文件。
- `reopen` → `SupportDesk.reopen_ticket(ticket_id, reason)`：重新打开已关闭工单。两个参数均须为去首尾空白后非空的字符串，标识按去空白后的值区分大小写查找，原因内部的空白、换行与标点原样保留。只允许存在且状态为 `closed` 的工单重开；成功返回完整工单，将 `status` 变为 `open`、`resolution` 变为 `null`，并按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后仍可读取。每次成功重开时在工单的 `reopen_history` 数组末尾追加一条记录，含 `reason` 与 `resolution`，分别保存规范化后的原因与重开前的解决说明；若工单带有 `closed_at`，该时间一并存入本条记录并从当前工单移除，没有该时间的工单仍只写这两个字段、不补写旧时间；旧工单缺少该字段时从空数组开始，且仅在成功重开时才新增该字段。再次关闭沿用现有规则（仍须已指派，解决说明覆盖为新值），之后重开继续向数组末尾追加，记录按成功重开的顺序排列。客户、主题、指派、备注、分类、优先级、登记时间、首次响应记录（含知识快照）与后续答复历史均保持原样，重开原因不追加到备注；已有首次响应的工单重开后仍禁止重复登记，没有首次响应的重开工单按原规则重新进入待响应队列，首次响应耗时仍以原 `opened_at` 计算，无登记时间的旧工单不补写时间字段。重开工单重新进入待处理队列，现有统计与队列均按重开后的状态反映当前数据。已发布的知识条目与既有答复快照不受影响；重开不释放来源工单的发布占用，发布过的工单不能再次发布，未发布过的工单须再次关闭后才能发布。其他公开入口保持既有语义，已关闭工单仍只有本入口可以恢复处理。工单不存在、尚未关闭、参数类型不符或去空白后为空均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件，也不留下重开记录。
- `list` → `SupportDesk.list_tickets(...)`。参数名见 `core.py` 的公开方法签名。
- `category-set` → `SupportDesk.set_category(ticket_id, category)`：为工单登记至多一个类别。`ticket_id` 去除首尾空白后须非空，按去空白后的值区分大小写查找；`category` 去除首尾空白后须为非空字符串，内部空白与标点原样保留，比较区分大小写。`category` 为 `null`（Python `None`）时清除分类并移除 `category` 字段（该参数必填，省略按缺少参数处理）。成功返回完整工单并按现有方式保存，重新创建 `SupportDesk` 后仍可读取。重复设置相同类别、或清除原本未分类的工单仍成功。只允许存在且未关闭的工单，已关闭工单不能设置或清除；未指派、无 `opened_at` 或已首次响应不影响未关闭工单分类。参数类型不符、去空白后为空、工单不存在或已关闭均抛出 `ValueError`；缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件，且不改变其他字段或知识条目。
- `category-list` → `SupportDesk.list_by_category(category, status=None)`：按类别查看工单。`category` 为必填参数，按上述规则精确匹配；`null`（Python `None`）只查询未分类工单（旧工单缺少 `category` 即视为未分类，不补写）。`status` 省略或为 `null` 时同时包括 open 和 closed，指定为 `open`/`closed` 时须同时满足类别与状态两个条件；非法状态抛出 `ValueError`。返回按 `ticket_id` 区分大小写升序排列的完整工单数组，已关闭工单也可查到；无匹配、无工单或数据目录不存在均返回 `[]`。只读，不创建目录或文件，不补写缺失的 `category` 字段；类别类型不符或去空白后为空抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`。
- `category-auto` → `SupportDesk.auto_categorize(rules)`：按客户问题关键词批量归类未分类工单，供后续 `route-assign` 等按分类分派使用。`rules` 必填，只接受非空数组，每项为只含 `category`、`query` 两个键的对象，缺键、多键或非对象均抛出 `ValueError`；`category` 与 `query` 都须为字符串且去除首尾空白后非空，不接受 `null`、数字、布尔等非字符串，类别与查询全为空白也拒绝；类别内部空白原样保留、比较区分大小写（取去首尾空白后的值），允许多条规则指向同一类别，规则在数组中的顺序决定优先级。`query` 去除首尾空白后按空白拆词，以 Unicode casefold 语义忽略大小写，标点作为词的一部分按字面匹配；每个词都要作为连续子串出现在工单主题或某条客户追问（`customer_messages[].message`）正文中，不同词可以命中不同记录，但单个词不能跨记录拼接；客户名称、备注、解决说明、客服答复（首次响应与后续答复正文及知识快照）与知识内容均不参与匹配。只有状态为 `open` 且 `category` 缺失或为 `null` 的工单是候选，不受指派、登记时间或首次响应影响；每单取首条命中规则的类别，没有命中就保持未分类，已有分类的未结工单与已关闭工单保持原样。旧工单缺少追问历史或历史为空时只匹配主题，读取与未命中都不补写该字段。整次归类全部成功或全部不变，任一规则结构或文本非法均抛出 `ValueError`，即使没有候选工单也照常校验；缺少 `rules` 或出现未知顶层参数抛出 `TypeError`；拒绝时不修改数据、不创建目录或文件。返回只含 `classified` 与 `remaining` 的对象：`classified` 为本次成功归类的完整工单数组，`remaining` 为仍未分类的候选工单标识数组，两者各按 `ticket_id` 区分大小写升序排列。只有成功归类时才沿用现有方式保存到 `root/data.json`，仅新增或更新对应工单的 `category` 字段，其他工单字段、答复快照与知识资料保留，规则不保存；重新创建 `SupportDesk` 后读取结果一致，并可被 `route-assign` 等按分类入口使用相同结果。没有成功归类时返回空 `classified` 与相应 `remaining`，数据目录不存在时两个数组均为空，均不写文件、不创建目录。既有公开入口与 `demo` 保持原行为，不自动触发归类。
- `ticket-search` → `SupportDesk.search_tickets(query, status=None, category=_UNSET, offset=0, limit=20)`：按内容搜索工单。`query` 必填，须为非空白字符串，去除首尾空白后按空白拆词，以 Unicode casefold 语义忽略大小写，标点按字面匹配。每个词均需作为连续子串出现在客户名称、主题、某条备注、解决说明或某条答复正文中，不同词可以命中不同字段或不同记录，但单个词不能跨字段或跨记录拼接；答复正文包括首次响应（`first_response.message`）与后续答复（`replies[].message`），知识答复按已保存的正文参与搜索，知识快照的其他字段不参与；`ticket_id`、指派人、分类与当前知识条目不参与搜索。`status` 省略或为 `null` 时同时包括 open 和 closed，否则只接受原值 `open`/`closed`。`category` 省略时不限分类，显式 `null` 只匹配未分类工单（旧工单缺少 `category` 即视为未分类，不补写），字符串去除首尾空白后区分大小写精确匹配，内部空白原样保留；`status` 与 `category` 按交集生效。`offset` 默认 0，只接受非负整数；`limit` 默认 20，只接受 1 至 100 的整数；两者均拒绝布尔值、浮点、字符串和 `null`。返回 `{"total": ..., "items": [...]}`，`total` 为分页前的匹配总数，`items` 为完整工单数组，先按 `ticket_id` 区分大小写升序排序再分页；`offset` 达到或超过总数时 `items` 为 `[]`、`total` 保留实际数量。无匹配、无工单或数据目录不存在时返回 `{"total": 0, "items": []}`。只读，成功或失败都不创建目录或文件、不修改数据、不补写字段；首次响应为空或缺少答复历史时视为没有对应正文。`query` 非字符串或全为空白、`category` 非字符串且非 `null` 或全为空白、`status` 非法、分页参数非法均抛出 `ValueError`，缺少 `query` 或出现未知参数抛出 `TypeError`。
- `respond` → `SupportDesk.respond(...)`：登记首次响应，参数为 `ticket_id`、`message`、`responded_at`（非负整数分钟，不得早于 `opened_at`，相等允许），返回完整工单；不改变状态、指派、备注或解决说明。记录只有 `message` 与 `responded_at`，不含 `knowledge`。
- `reply` → `SupportDesk.reply(ticket_id, message, replied_at)`：在已有首次响应之后追加工单后续答复。`ticket_id` 去除首尾空白后须非空，按去空白后的值区分大小写查找；`message` 去除首尾空白后须为非空字符串，正文内部的空白与换行原样保留；`replied_at` 只接受非负整数分钟（拒绝布尔值、浮点、字符串和 `null`），不得早于首次响应时间或最后一条后续答复时间，同一分钟允许继续追加。只允许存在、未关闭、有 `opened_at` 且已有非空 `first_response` 的工单使用，未指派不影响。成功返回完整工单，在 `replies` 数组末尾追加一条只含 `message` 与 `replied_at` 的记录并按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后仍可读取；旧工单缺少 `replies` 时按空历史处理，仅首次成功追加时才新增该字段，登记与读取均不补写。重复提交相同正文与时间仍追加新记录。工单的状态、指派、备注、解决说明、优先级、首次响应记录及其他字段均不变。参数类型或值非法、工单不存在或已关闭、缺少登记时间或首次响应、时间倒退均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件。
- `receive` → `SupportDesk.receive(ticket_id, message, received_at)`：登记客户在工单上的追问。三个参数均必填：`ticket_id`、`message` 去除首尾空白后须为非空字符串，标识按去空白后的值区分大小写查找，正文内部的空白与换行原样保留；`received_at` 只接受非负整数分钟（拒绝布尔值、浮点、字符串和 `null`）。只允许存在、状态为 `open` 且有 `opened_at` 的工单登记追问，未指派或尚未首次响应不影响。`received_at` 不得早于工单的 `opened_at`，也不得早于 `customer_messages` 末条追问时间，同一分钟允许继续追加。成功返回完整工单，在 `customer_messages` 数组末尾追加一条只含 `message` 与 `received_at` 的记录并按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后仍可读取；旧工单缺少 `customer_messages` 时按空历史处理，仅首次成功追加时才新增该字段，登记与读取均不补写。重复提交相同正文与时间仍追加新记录。追问不加入备注、不参与既有工单搜索，也不计入响应统计；工单的状态、指派、备注、解决说明、优先级、首次响应记录、后续答复及其他字段均不变。参数类型或值非法、工单不存在、已关闭或缺少登记时间、时间倒退均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件。关闭与重开工单保留 `customer_messages` 历史，关闭后退出客户待答复队列，重开后按当前数据重新判断。
- `priority-set` → `SupportDesk.set_priority(ticket_id, priority)`：设置工单优先级，`priority` 仅限 `low`、`normal`、`high`、`urgent`。两个参数均须为非空字符串，先去除首尾空白再区分大小写匹配；只允许针对存在且未关闭的工单，成功返回完整工单并写入 `priority` 字段。重复设置相同值同样成功，不追加备注，不改变状态、指派、解决说明或首次响应记录。参数类型错误、去空白后为空、不支持的优先级、工单不存在或已关闭均报错且不写数据、不创建数据文件。
- `priority-queue` → `SupportDesk.priority_queue()`：返回待处理队列数组，每项含 `ticket`（原样完整工单，不补字段）与 `priority`（有效优先级）。包含全部未关闭工单（已首次响应、未指派、无 `opened_at` 的均在内），排除已关闭工单；按 `urgent`、`high`、`normal`、`low` 排序，同级按 `ticket_id` 区分大小写升序。未设置 `priority` 的工单按 `normal` 排序。无工单、只有已关闭工单或数据目录不存在时返回 `[]`；只读，不创建目录、不写文件，可省略输入文件。
- `priority-escalate` → `SupportDesk.escalate_overdue(as_of, response_minutes=30, customer_minutes=30)`：批量把模拟时刻 `as_of`（非负整数分钟）仍超时等待的未结工单提升为 `urgent`。`response_minutes` 与 `customer_minutes` 均为正整数分钟、默认 30，分别控制首次响应与客户追问两类等待目标；三者均拒绝布尔值、浮点、字符串和 `null`，类型或取值非法抛出 `ValueError`，缺少 `as_of` 或出现未知参数抛出 `TypeError`。已关闭工单不参与，未指派不影响，缺少答复或追问历史按空记录处理，手写答复与知识答复同等计算。首次响应缺失、为 `null` 或为空对象 `{}` 的工单属于待首次响应：有 `opened_at` 时等待自登记时间算到 `as_of`，严格超过 `response_minutes` 即超时；无 `opened_at` 的工单不参加此类升级。追问类只检查有 `customer_messages` 追问历史的未结工单：答复边界取首次响应时间与全部后续答复时间（`replies[].replied_at`）的最大值，与边界同一分钟的追问视为已答复，仅严格晚于边界的追问尚待答复；没有任何答复时边界为空、全部追问尚待答复；等待自最早未答复追问起算（重复追问记录不改变这一取时规则），严格超过 `customer_minutes` 才超时，相等不超时。两类等待同时超时的工单只处理一次，原本已是 `urgent` 的工单照常参与超时与时间合法性检查但不会出现在结果中、也不重复写入。判断超时前，待首次响应工单的 `opened_at`，或追问工单涉及的任一追问时间、首次响应或后续答复时间晚于 `as_of` 时，整次调用抛出 `ValueError`，已有 `urgent` 工单也照常检查，不返回部分结果、不留下部分修改。返回真正被升级的完整工单数组，按 `ticket_id` 区分大小写升序排列；成功只把这些工单的 `priority` 改为 `urgent` 并按现有方式保存到 `root/data.json`，重新创建 `SupportDesk` 后 `get` 读取同样结果，现有按优先级工作的队列（如 `priority-queue`）、分派（如 `auto-assign`、`handover`、`route-assign`）与报告均采用新值；不追加备注、不刷新任何响应时间，其他字段与知识资料保留。没有工单需要升级时返回 `[]` 且不写数据、不创建目录或文件；参数或时间非法时同样不写入。其他公开入口与 `demo` 保持原语义，任何既有操作都不自动触发升级。
- `response-stats` → `SupportDesk.response_stats()`：汇总首次响应耗时（`timed`、`responded`、`pending`、`untimed` 计数及 `average_minutes`、`max_minutes`），无参数，可省略输入文件，不写数据。
- `response-queue` → `SupportDesk.response_queue(as_of, target_minutes=30)`：查看模拟时刻 `as_of`（非负整数分钟）仍待首次响应的工单队列，`target_minutes` 为正整数分钟。返回 `{"untimed": n, "items": [...]}`：未关闭且无首次响应且有 `opened_at` 的工单进入 `items`，每项含完整工单 `ticket`、`waiting_minutes`（`as_of - opened_at`）与 `overdue`（等待严格大于目标才为真），按 `opened_at` 升序、同分钟按 `ticket_id` 升序；缺少 `opened_at` 的待响应工单只计入 `untimed`。任一入队工单的 `opened_at` 晚于 `as_of` 则整个查询报错。只读，不写数据。
- `follow-up-queue` → `SupportDesk.follow_up_queue(as_of, target_minutes=60)`：查看模拟时刻 `as_of`（非负整数分钟）已答复工单的跟进队列，`target_minutes` 为正整数分钟，默认 60。返回 `{"as_of": ..., "items": [...]}`，只含这两个键。状态为 `open` 且首次响应为非空对象的工单入队，未指派不影响；已关闭工单，以及首次响应缺失、为 `null` 或为空对象 `{}` 的工单排除，即使存在后续答复记录也不入队；缺少 `opened_at` 不影响符合条件的工单入队。每项只含 `ticket`（原样完整工单，不补字段）、`priority`（工单未设优先级时取 `normal`）、`last_answered_at`、`waiting_minutes` 与 `overdue`：有后续答复时最后答复时间取 `replies` 末条的 `replied_at`，`replies` 历史缺失或为空数组时取首次响应的 `responded_at`；等待时间为 `as_of - last_answered_at`，等待严格大于目标时 `overdue` 为 `true`，相等为 `false`。队列按 `last_answered_at` 升序，同一分钟依次按 `urgent`、`high`、`normal`、`low` 排序，再按 `ticket_id` 区分大小写升序。新的后续答复刷新等待时间，备注或知识条目变更不刷新，工单重开沿用已有首次响应与后续答复历史。任一入队工单的首次响应时间或任一后续答复时间晚于 `as_of`，整个查询抛出 `ValueError` 而不返回部分结果，被排除的工单不参与该检查。`as_of` 须为非负整数、`target_minutes` 须为正整数，两者均拒绝布尔值、浮点、字符串与 `null`；非法参数抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`。无符合条件的工单或数据目录不存在时 `items` 为 `[]`。只读，不创建目录或文件、不修改数据、不补写字段，重新创建 `SupportDesk` 后同数据同参数结果一致。
- `customer-queue` → `SupportDesk.customer_queue(as_of, target_minutes=30)`：查看模拟时刻 `as_of`（非负整数分钟）仍待答复的客户追问，`target_minutes` 为正整数分钟，默认 30。只检查状态为 `open` 且有 `customer_messages` 追问历史的工单，未指派不影响；已关闭工单，以及没有追问历史的工单（即使已有首次响应）一律不参与；缺少 `opened_at` 的工单不会有追问历史，因而不参与。首次响应缺失、为 `null` 或为空对象 `{}` 视为尚无该答复；缺少后续答复或追问历史时按空数组处理，不补写。答复边界取首次响应时间与全部后续答复时间（`replies[].replied_at`）中的最大值；没有任何答复时边界为空，全部追问都未答复。追问时间严格晚于边界才视为未答复，与边界同一分钟视为已被覆盖；每个工单至多返回一项。`as_of` 之前任一入队工单的追问时间、首次响应时间或后续答复时间晚于 `as_of`，整个查询抛出 `ValueError` 而不返回部分结果，被排除的工单不参与该检查。返回数组，每项只含 `ticket`（原样完整工单，不补字段）、`count`（未答复追问数）、`waiting_minutes`（自最早未答复追问时间起算到 `as_of` 的等待分钟）与 `overdue`（等待严格超过 `target_minutes` 为 `true`，相等为 `false`）；追问已全部被答复覆盖的工单排除，无数据或无匹配时返回 `[]`。结果按最早未答复追问时间升序，同一分钟按 `ticket_id` 区分大小写升序。关闭工单保留追问历史但退出队列，重开后按当前数据重新判断，新的答复覆盖相应追问。`as_of` 须为非负整数、`target_minutes` 须为正整数，两者均拒绝布尔值、浮点、字符串与 `null`；非法参数抛出 `ValueError`，缺少 `as_of` 或出现未知参数抛出 `TypeError`。只读，成功或失败都不创建目录或文件、不修改数据、不补写字段，重新创建 `SupportDesk` 后同数据同参数结果一致。
- `pending-queue` → `SupportDesk.pending_queue(as_of, response_minutes=30, customer_minutes=30)`：统一待答复队列，把待首次响应与待答复客户追问合并为一张工单一项的视图。`as_of` 为必填的非负整数分钟，`response_minutes` 与 `customer_minutes` 为可选正整数分钟、默认均为 30；三者均拒绝布尔值、浮点、字符串和 `null`，非法值抛出 `ValueError`，缺少 `as_of` 或出现未知参数抛出 `TypeError`，空数据也照常校验。只处理状态为 `open` 的工单，未指派不影响；已关闭工单不参与、也不参与任何时间检查。首次响应缺失、为 `null` 或为空对象 `{}` 即未响应：有 `opened_at` 时首次响应等待自登记时间算到 `as_of`；无登记时间的工单不产生首次响应等待值，只计入 `untimed`。客户等待从最早未答复追问起算：答复边界取首次响应时间与全部后续答复时间（`replies[].replied_at`）的最大值，严格晚于边界的追问才未答复，与边界同一分钟视为已答复；没有任何答复时全部追问未答复，重复追问分别计数；缺少追问或答复历史按空记录处理，手写与知识答复等同计算。返回只含 `untimed` 与 `items`：每项只含 `ticket`（原样完整工单，不补字段）、`response_wait`（`as_of - opened_at`，无该类等待时为 `null`）、`customer_wait`（`as_of` 减最早未答复追问时间，无该类等待时为 `null`）、`count`（未答复追问数）与 `overdue`。任一非空等待严格超过对应目标才令 `overdue` 为 `true`，相等不超时；两类等待都不存在（追问全部已覆盖且已首次响应，或无登记时间的未响应工单也没有未答复追问）的工单不入队，无登记时间的未响应工单仍计入 `untimed`。排序先排超时工单，再按 `urgent`、`high`、`normal`、`low`（缺优先级按 `normal`），同级按两类非空等待值的最大值降序，最后按 `ticket_id` 区分大小写升序。待首次响应工单的 `opened_at` 晚于 `as_of`，或有追问历史的未结工单任一追问、首次响应或后续答复时间晚于 `as_of`，均令整个查询抛出 `ValueError` 而不返回部分结果，即使追问已被答复覆盖也检查。关闭使工单退出队列，重开沿用历史重新判断。无数据返回 `untimed` 为 0、`items` 为 `[]`。只读，查询无论成败都不写数据、不创建目录或文件、不补写旧字段，重新创建 `SupportDesk` 后同数据同参数结果一致；既有公开入口与 `demo` 保持原行为。
- `customer-response-report` → `SupportDesk.customer_response_report(as_of, since=0, until=null)`：在模拟时刻 `as_of`（非负整数分钟）统计每条客户追问的答复时效。可选 `since`（默认 `0`）与 `until`（默认 `null`）按追问接收时间选择半开统计区间：包含 `since`、不包含 `until`，`until` 省略或为 `null` 时无上界，两者相等时为空区间；筛选只看追问接收时间，不看登记、答复或结案时间，窗口边界允许晚于 `as_of`。open 与 closed 工单都参与，未指派或缺少 `opened_at` 不影响；没有 `customer_messages` 追问历史、或没有追问落入区间的工单不参与（即使已有答复），重复追问记录不合并，每条独立计数、保留在原数组中的零起始下标。首次响应缺失、为 `null` 或为空对象 `{}` 视为无该答复；缺少追问或后续答复历史按空数组处理，不补写。手写答复与知识答复同等处理：答复时间集合取非空首次响应的 `responded_at` 与全部 `replies[].replied_at`。匹配只看时间、不看调用顺序，也不受区间限制（答复可落在区间之外）：取时间不早于该追问（大于等于）的最早答复作为其答复，同一分钟计零耗时；一条答复可覆盖多条追问。匹配成功的追问 `outcome` 为 `answered`，`answered_at` 为所匹配答复时间、`response_minutes` 为答复时间减追问时间；未匹配的追问在 open 工单上为 `pending`，在 closed 工单上为 `closed_without_answer`，两者的 `answered_at` 与 `response_minutes` 均为 `null`；关闭与重开按工单当前状态归类。返回只含 `as_of`、`summary`、`items` 的对象：`items` 每项只含 `ticket_id`、`index`、`received_at`、`answered_at`、`response_minutes`、`outcome`，依次按追问时间、区分大小写的工单标识、下标升序排列；`summary` 只含 `total`、`answered`、`pending`、`closed_without_answer`、`average_minutes`、`max_minutes`，分别为入选追问总数、三类结果计数及入选已答复耗时的算术平均与最大值，没有任何入选已答复追问时两项耗时统计为 `null`。任一入选追问、或其所属工单的任一答复时间晚于 `as_of`，整个查询抛出 `ValueError` 而不返回部分结果；未入选追问及没有入选追问的工单不触发该检查。`as_of` 只接受非负整数分钟，布尔值、浮点、字符串、`null` 或负数均抛出 `ValueError`；`since` 与非 `null` 的 `until` 同样只接受非布尔的非负整数分钟，`until` 早于 `since` 抛出 `ValueError`；缺少 `as_of` 或出现未知参数抛出 `TypeError`；空数据也校验参数。空区间、无匹配或数据目录不存在时返回零计数、空 `items` 与 `null` 耗时统计。只读，查询无论成败都不写数据、不创建目录或文件、不补写字段，重新创建 `SupportDesk` 后同数据同参数结果一致；其他公开入口与 demo 保持原语义。
- `response-target-report` → `SupportDesk.response_target_report(as_of, targets=None, since=None, until=None, service_periods=None)`：按优先级判断首次响应是否达标，只反映当前数据。`as_of` 为非负整数分钟；`targets` 省略或为 `null` 时 urgent、high、normal、low 的目标分别为 5、15、30、60 分钟，传入对象时仅覆盖指定项（空对象等于默认值），目标值须为正整数。可选 `since` 与 `until`（默认均为 `null`）按 `opened_at` 登记时间选择半开统计窗口：包含 `since`、不包含 `until`，任一边界省略或为 `null` 表示该方向不限，两界相等时为空窗口；筛选只看登记时间，不看答复、结案或重开时间，窗口边界允许晚于 `as_of`；无 `opened_at` 的旧工单在窗口查询中不参与，两界都省略或为 `null` 时不过滤、保留含 `untimed` 计数的原结果。可选 `service_periods`（省略或为 `null` 时完整保留按自然分钟统计的原结果）为客服服务时段数组，每项是 `[start, end]` 形式的半开区间：包含起点分钟、不包含终点分钟，两端点均为模拟时钟上的非负整数分钟且 `start < end`；空数组表示没有任何服务时间。重叠、重复或首尾相接的区间合并后覆盖分钟只计一次，输入顺序不影响结果；区间可早于登记时间或晚于 `as_of`，统计区间之外的分钟不计入，时段不隐含周期重复，也不保存到数据中。传时段时，有登记时间且已首次响应的入选工单只累计自登记到首次响应之间与服务区间相交的分钟作为响应耗时（例如时段 `[[10,20],[30,50]]`、15 登记 40 响应计 15 分钟），耗时不超过目标计 `on_time`、否则计 `late`；未响应且未关闭的入选工单自登记到 `as_of` 按同一口径累计，耗时严格超过目标才计 `overdue`（同样的待响应工单在 `as_of` 为 40 时不超时、41 时超时），耗时等于目标仍达标且不超时；空服务数组下，有登记时间的已响应工单耗时均为 0 而全部达标，待响应工单耗时均为 0 而均不超时。返回 `{"as_of": ..., "groups": [...]}`，groups 按 urgent、high、normal、low 排列，每组含 `priority`、`target_minutes`、整数计数 `responded`、`on_time`、`late`、`pending`、`overdue`、`untimed`、`closed_without_response` 及 `on_time_rate`。入选工单按当前状态与优先级统计，缺少 `priority` 的旧工单按 normal 统计且不补写该字段；无 `opened_at` 的工单只计 `untimed`；有登记时间且已有首次响应的工单（无论是否关闭）计 `responded`，首次响应即使在窗口外也参与，后续答复不替代首次响应；有登记时间、未响应且已关闭的工单计 `closed_without_response`，不按时段重新判定；其余未响应工单计 `pending`。`on_time_rate` 为 `on_time / responded`（0 至 1），分母为零时为 `null`。任一入选工单的 `opened_at` 或已有响应时间晚于 `as_of`，整个查询报错而不返回部分结果；空服务数组或时间落在非服务区间均不免除该检查，未入选工单的未来时间不影响查询。非法 `as_of`、非对象的非 `null` `targets`、未知优先级键或非正整数目标值均报错；非 `null` 的 `since`、`until` 只接受非布尔的非负整数分钟，两界都有值且 `until` 早于 `since` 同样报错；非数组且非 `null` 的 `service_periods`、非 `[start, end]` 结构的区间、非整数或布尔端点、负数端点及 `start >= end` 均抛出 `ValueError`；缺少 `as_of` 或出现未知参数抛出 `TypeError`，空数据、空窗口或空服务数组也校验全部参数。空窗口、无匹配、空数据或数据目录不存在时返回四组零计数与 `null` 达标率；只读，查询无论成败都不创建目录或文件、不修改数据、不补写字段、不保存服务时段，重新创建 `SupportDesk` 后同数据同参数结果一致。
- `assignee-workload-report` → `SupportDesk.assignee_workload_report(as_of, response_minutes=30, follow_up_minutes=60)`：按处理人统计模拟时刻 `as_of`（非负整数分钟）的未结工单工作量，只反映当前数据。`response_minutes` 与 `follow_up_minutes` 为正整数分钟，默认分别为 30、60，均拒绝布尔值、浮点、字符串与 `null`。返回 `{"as_of": ..., "groups": [...]}`，只含这两个键，`as_of` 为原值。只统计状态为 `open` 的工单，按 `assignee` 原值区分大小写分组，`assignee` 缺失或为 `null` 的工单归入 `assignee` 为 `null` 的未指派组；空组不返回，未指派组排在最前，其余组按名称区分大小写升序。每组只含 `assignee`、`open`、`pending`、`overdue`、`follow_up`、`follow_up_overdue`、`untimed`，后六项为非负整数计数：`open` 计全组工单；首次响应缺失、为 `null` 或为空对象 `{}` 即未响应，有 `opened_at` 时计 `pending`，等待自登记时间算到 `as_of`，严格大于 `response_minutes` 时同时计 `overdue`，无登记时间计 `untimed`；首次响应为非空对象即计 `follow_up`（无登记时间也计入），跟进等待自 `replies` 末条 `replied_at` 起算，`replies` 缺失或为空数组时自首次响应 `responded_at` 起算，严格大于 `follow_up_minutes` 时同时计 `follow_up_overdue`；手写答复与知识答复同等计算，备注与知识修订不刷新等待。任一组内待响应工单的 `opened_at`、或跟进工单的首次响应时间及任一后续答复时间晚于 `as_of`，整个报告抛出 `ValueError` 而不返回部分结果；已关闭工单不参与该检查。非法参数抛出 `ValueError`，缺少 `as_of` 或出现未知参数抛出 `TypeError`。无未结工单或数据目录不存在时 `groups` 为 `[]`。只读，查询无论成败都不创建目录或文件、不修改数据、不补写字段，重新创建 `SupportDesk` 后同数据同参数结果一致；改派按当前归属统计，关闭移出报告，重开沿用已有答复时间。
- `knowledge-publish` → `SupportDesk.publish_knowledge(article_id, ticket_id)`：从已关闭工单发布知识条目，条目含 `article_id`、`source_ticket_id`、`title`（工单 subject）、`content`（工单 resolution）四个字段并返回完整条目。两个标识去除首尾空白、区分大小写；同一 root 内 `article_id` 唯一，每个工单只可发布一次。参数非字符串或去空白后为空、标识重复、工单已发布过、工单不存在或未关闭均报错且不写数据；来源工单保持原样，无 `opened_at` 或首次响应记录的已关闭工单也可发布。
- `knowledge-update` → `SupportDesk.update_knowledge(article_id, title, content)`：修订已发布的知识条目，替换其标题与正文，`article_id`、`source_ticket_id` 两个标识保持原值，成功返回四字段完整条目。三个参数均须为去首尾空白后非空的字符串（标题与正文内部的换行、空格和标点原样保留），`article_id` 按去空白后的值区分大小写查找。规范化后的标题或正文与当前内容实际不同时，保留新旧内容并新增一个版本；重复提交相同的规范化内容仍成功，不增加版本。新发布条目的初始内容为版本 1，各条目独立连续编号；缺少版本资料的旧条目以当前内容作为版本 1，不反推旧修订。类型不符或去空白后为空、条目不存在抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件。修订后检索按既有规则使用当前标题与正文；新的 `knowledge-respond` 使用当前正文并保存当前四字段快照，既有工单的首次响应正文、时间与知识快照保持原样，来源工单与其他工单均不受影响。修订不改变启停状态，无知识数据时按条目不存在拒绝。
- `knowledge-history` → `SupportDesk.knowledge_history(article_id)`：查询知识条目的修订历史。`article_id` 去除首尾空白后须非空，按去空白后的值区分大小写查找。返回按 `revision` 升序排列的数组，每项只含 `revision`、`title`、`content`，不包含条目标识、来源工单或启停状态。新发布条目的历史以版本 1 为初始内容；缺少版本资料的旧条目以当前标题与正文作为版本 1 返回，不反推旧修订，读取时不补写存储。已停用条目也可查询。只读，不创建目录或文件，不改动已存数据；标识类型不符或去空白后为空、条目不存在抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`。
- `knowledge-restore` → `SupportDesk.restore_knowledge(article_id, revision)`：将指定版本的标题和正文设为当前内容，返回既有四字段完整条目（`article_id`、`source_ticket_id`、`title`、`content`），条目标识、来源工单与启停状态保持原样，停用条目也可恢复。`article_id` 去除首尾空白后须非空并区分大小写查找；`revision` 只接受正整数（拒绝布尔值、浮点、字符串和 `null`）。目标内容与当前不同时追加新版本：不能删除或改写旧版本，也不倒退版本号（例如正文从甲改为乙后恢复版本 1，历史依次保留甲、乙、甲三个版本，随后修改生成版本 4）；目标内容与当前相同时恢复成功且不增加版本。旧条目恢复版本 1 即其当前内容时同样成功且不增加版本。历史与当前内容一起保存在 `root/data.json`，重新创建 `SupportDesk` 后结果一致。标识非法、条目不存在、版本非法或版本不存在均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件，不能留下仅内容或仅历史变化的结果。恢复后检索与新的知识答复使用恢复后的当前内容，既有首次响应正文、时间与四字段快照保持原样。
- `knowledge-search` → `SupportDesk.search_knowledge(query=None)`：检索知识条目。`query` 省略或为 `null` 时返回全部；否则须为非空白字符串，去除首尾空白后按空白拆词，以 Unicode casefold 语义忽略大小写，每个词均需作为连续子串出现在 `title` 或 `content` 中（可分别命中不同字段），标点按字面匹配。返回完整条目数组，按 `article_id` 升序，无匹配返回 `[]`。已停用条目不出现在任何结果中。只读，不写数据；无知识条目或空目录返回 `[]`。
- `knowledge-enabled-set` → `SupportDesk.set_knowledge_enabled(article_id, enabled)`：停用或恢复知识条目。`article_id` 去除首尾空白后须非空、按去空白后的值区分大小写查找；`enabled` 只接受布尔值。成功返回 `{"article": ..., "enabled": ...}`，`article` 为原有四字段完整条目，`enabled` 为实际布尔状态；状态保存在 `root/data.json`，重新创建 `SupportDesk` 后仍生效，重复设置同一状态也成功。历史条目缺少状态信息时视为启用，新发布条目默认启用，读取时不补写状态。停用后 `knowledge-search`（含省略或为 `null` 的 `query`）只返回启用条目，`knowledge-respond` 引用停用条目抛出 `ValueError` 且不留首次响应，恢复后可按现有前置条件引用。停用不改变条目的四个字段，也不释放条目标识或来源工单的发布占用；`knowledge-update` 仍可修订停用条目并返回四字段条目，修订不会恢复启用。已保存的首次响应正文、时间与知识快照保持原样，停用状态不出现在发布、修订、检索的条目结果中。标识类型不符或去空白后为空、`enabled` 非布尔值、条目不存在均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件，也不改变工单和历史答复。
- `knowledge-respond` → `SupportDesk.respond_with_knowledge(ticket_id, article_id, responded_at, revision=None)`：引用一条已发布的知识条目答复工单，登记首次响应，不接收自定义正文。两个标识须为非空字符串，去除首尾空白后区分大小写查找；`responded_at` 为非负整数分钟（拒绝布尔值与浮点），允许等于 `opened_at`，早于则拒绝。可选 `revision` 省略或为 `null` 时引用条目当前内容，响应记录不含版本字段；指定时只接受正整数（布尔值、浮点、字符串、零和负数均抛出 `ValueError`），引用该版本的标题与正文。成功返回并保存完整目标工单，其 `first_response` 含 `message`（等于所引用版本的正文）、`responded_at` 与 `knowledge`（`article_id`、`source_ticket_id` 两个标识保持原值，`title` 与 `content` 取自当前内容或所选版本的四字段快照）；指定版本时在同层增加 `knowledge_revision`，值为所选版本号，省略或为 `null` 时不写该字段。重新创建 `SupportDesk` 后仍可读取同样的响应与快照。只允许存在、未关闭、有 `opened_at` 且尚无首次响应的工单使用，未指派不影响；与手写 `respond` 共用首次响应唯一性，任一种登记成功后两种入口均按已有响应拒绝。停用条目的任何版本均不能引用；缺少历史资料的旧条目仅以当前内容作为版本 1，引用版本 1 时不补写历史，其他版本按版本不存在拒绝。参数类型或取值非法、缺少登记时间、工单不存在或已关闭、知识条目或指定版本不存在、条目已停用均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`，失败不写数据、不创建目录或文件、不留部分响应。成功后知识条目当前内容、启停状态与版本历史、来源工单均保持原样，目标工单的状态、指派、备注、解决说明和优先级均不变。后续修订、恢复版本、停用或工单重开都不改写已保存的响应。
- `knowledge-reply` → `SupportDesk.reply_with_knowledge(ticket_id, article_id, replied_at, revision=None)`：引用已发布知识条目追加后续答复，不接收自定义正文。两个标识去除首尾空白后须非空、区分大小写查找；时间参数与 `reply` 相同，只接受非负整数分钟，不得早于首次响应时间或最后一条后续答复时间，同分钟允许追加。可选 `revision` 省略或为 `null` 时引用当前内容，答复记录不含版本字段；指定时只接受正整数（布尔值、浮点、字符串、零和负数均抛出 `ValueError`）。工单前置条件与 `reply` 一致（存在、未关闭、有 `opened_at` 且已有非空 `first_response`，未指派不影响）；知识条目须存在且启用，缺少启停信息的旧条目仍视为启用，停用条目的任何版本均不能引用。成功返回并保存完整工单，在 `replies` 数组末尾追加记录，含 `message`（等于当前内容或所选版本的正文）、`replied_at` 与 `knowledge`（`article_id`、`source_ticket_id` 保持原值，`title`、`content` 取自当前内容或所选版本的四字段快照）；指定版本时在同层增加 `knowledge_revision` 字段，值为所选版本号，省略或为 `null` 时不写该字段。缺少历史资料的旧条目仅以当前内容作为版本 1，引用时不补写历史。重新创建 `SupportDesk` 后仍可读取。后续修订、恢复版本、停用条目或工单重开均不改写已保存的后续答复；重复提交相同条目、版本与时间仍追加新记录。参数类型或值非法、工单不满足条件、条目不存在或已停用、时间倒退均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据、不创建目录或文件。关闭与重开工单保留 `replies` 历史，重开后继续追加时仍须遵守原时间顺序（不早于首次响应与最后一条后续答复）。
- `knowledge-usage-report` → `SupportDesk.knowledge_usage_report(since=0, until=None)`：按时间范围统计知识条目的引用情况，只根据当前保存的答复记录计算。`since` 与 `until` 为模拟时钟的非负整数分钟（拒绝布尔值、浮点、字符串），范围包含 `since`、不包含 `until`；`until` 省略或为 `null` 表示无上界，与 `since` 相等时所有引用计数为零。返回按 `article_id` 区分大小写升序排列的数组，包含全部已发布知识，停用或从未被引用的条目也在内。每项含 `article`（当前四字段完整条目）、`enabled`（当前布尔启停状态，缺少状态信息时视为 `true`）、`first_responses` 与 `replies`（范围内带知识快照的首次响应与后续答复次数，分别按 `responded_at` 与 `replied_at` 落入范围判定，按快照的 `article_id` 精确归属）、`ticket_count`（这些引用涉及的不同工单数）与 `last_used_at`（范围内引用时间的最大值）；无引用时三个计数为 0、`last_used_at` 为 `null`。手写答复、备注与发布本身不计入；缺少首次响应或后续答复历史的旧工单按空记录处理，不补写字段。修订、恢复版本、停用条目以及关闭、重开工单均保留已存引用的计数与归属。无知识条目或数据目录不存在时返回 `[]`。只读，成功或失败都不创建目录、不写文件；`since` 为 `null`、时间参数非整数或为负、`until` 小于 `since` 均抛出 `ValueError`，出现未知参数抛出 `TypeError`。
- `knowledge-review-queue` → `SupportDesk.knowledge_review_queue(article_id, offset=0, limit=20, pending_only=False)`：列出引用了指定知识条目且快照已过期的未结工单。`article_id` 去除首尾空白后须非空，按去空白后的值区分大小写查找，条目不存在（含无数据）抛出 `ValueError`，停用条目也可查询。只检查 `open` 工单中带有该条目标识的知识答复（按快照 `article_id` 精确归属，区分大小写）：快照的 `title` 或 `content` 原值与条目当前内容不同即为过期，版本号、来源标识与启停状态不参与比较，引用旧版本但两项内容与当前相同则不算过期。返回 `{"total": ..., "items": [...]}`，`total` 为分页前匹配工单数，`items` 每项含完整 `ticket` 与 `references`；`references` 只列该工单引用此条目的过期答复，每条只含 `kind` 与 `index`，首次响应为 `{"kind": "first_response", "index": null}`，后续答复为 `{"kind": "reply", "index": 在原 replies 数组中的零起始下标}`，按首次响应在前、后续答复原顺序排列。工单按 `ticket_id` 区分大小写升序排序后分页；同一工单多处过期引用只计一次，手写答复、其他条目引用与内容未过期的引用不列入。关闭工单排除，重开后按当前内容重新判断；条目修订或恢复版本后以当前内容重新比较，既有快照保持原样。可选 `pending_only` 省略或为 `false` 时完整保留上述结果；为 `true` 时只列出仍过期且尚未针对条目当前标题、正文确认的引用：`references` 排除已确认引用，没有剩余引用的工单不入队，`total` 按过滤后的工单数计算，再沿用原排序与分页；`pending_only` 只接受布尔值，其他类型抛出 `ValueError`。`offset` 默认 0，只接受非负整数；`limit` 默认 20，只接受 1 至 100 的整数；两者均拒绝布尔值、浮点、字符串和 `null`，非法时抛出 `ValueError`，缺少 `article_id` 或出现未知参数抛出 `TypeError`。无匹配或 `offset` 达到或超过总数时 `items` 为 `[]`、`total` 保留实际数量。旧工单缺少首次响应或答复历史视为无对应引用，首次响应为 `null` 或空对象同样忽略；旧条目缺少版本历史不影响比较；旧数据没有确认资料时视为未确认。只读，成功或失败都不创建目录、不写文件、不补写字段。
- `knowledge-review` → `SupportDesk.review_knowledge(ticket_id, article_id)`：确认某工单对某知识条目的全部过期引用已复核。两个标识均须为去除首尾空白后非空的字符串，按去空白后的值区分大小写查找；只允许已存在且状态为 `open` 的工单与已存在的条目，停用条目也可确认，过期判断沿用 `knowledge-review-queue` 的规则。成功返回只含 `ticket_id`、`article_id`、`reviewed_count` 的对象，标识为规范化值，`reviewed_count` 为本次覆盖的全部过期引用数（已确认过的引用也计入）；重复确认同样成功，无过期引用时计数为零且不写数据。确认只覆盖提交时已有的过期引用，之后追加的引用即使快照相同也须独立复核；每条确认记录条目当时的标题与正文，当前内容不同于该引用最近一次确认时的标题或正文时原确认不再有效，恢复到最近一次确认的相同内容则再次有效，版本号与启停状态不参与判断。确认结果保存在 `root/data.json`，重新创建 `SupportDesk` 后仍生效，但不改写工单字段、知识条目、版本历史或答复快照；关闭工单被排除，重开保留确认并按当前内容判断，手写答复及其他条目的引用不受影响，其他公开入口与统计保持原语义。标识非法、工单不存在或已关闭、条目不存在均抛出 `ValueError`，缺少必填参数或出现未知参数抛出 `TypeError`；失败不写数据且不创建目录或文件。
- `knowledge-correct` → `SupportDesk.correct_knowledge(article_id, ticket_ids, replied_at)`：对一批工单批量补发某知识条目的当前内容说明，并同时确认这些工单对该条目的全部过期引用。三个参数均必填。`article_id` 与 `ticket_ids` 元素均须为去除首尾空白后非空的字符串，按去空白后的值区分大小写查找；`ticket_ids` 只接受非空数组，元素规范化后不得重复。条目须存在且启用，缺少启停信息的旧条目视为启用。每个所选工单须存在、状态为 `open`、有 `opened_at` 且有非空 `first_response`（未指派不影响），并至少有一处该条目的过期引用尚未针对当前标题、正文确认，判断沿用 `knowledge-review-queue` 的 `pending_only` 语义；旧工单缺少确认资料或答复历史按空记录处理。`replied_at` 只接受非布尔的非负整数分钟，不得早于任一所选工单的首次响应或末条后续答复时间，相等允许。成功按输入顺序返回完整工单数组：每单向 `replies` 末尾追加一条记录，含 `message`（等于条目当前正文）、`replied_at` 与四字段 `knowledge` 快照（`article_id`、`source_ticket_id`、`title`、`content`），不含 `knowledge_revision`，既有答复保持原样；同时针对当前标题与正文确认提交时该工单对本条目的全部过期引用（已确认过的也覆盖），使其退出待复核队列，普通复核查询仍显示这些快照过期的引用，后续内容变化与新增引用沿用既有确认规则。整次调用全部成功或全部不变：答复与确认一起保存在 `root/data.json`，重新创建 `SupportDesk` 后一致；任一标识或数组非法、条目不存在或停用、任一工单不满足条件、时间非法均抛出 `ValueError`，缺少参数或出现未知参数抛出 `TypeError`，失败不写数据、不创建目录或文件、不留下答复或确认。新增答复参与既有工单搜索、引用统计与跟进等待，其他工单字段与知识资料不变。

命令成功向标准输出打印 JSON 并返回 0；输入或本地文件错误向标准错误输出说明并返回 2。无参数的方法可省略输入文件。数据保存在 `root/data.json`，每次成功修改后保存；适用于单进程本地使用。

## 当前边界

当前没有外部消息集成或权限系统；时间由使用者提供（本地模拟时钟的非负整数分钟）。 不承诺并发写入或断电恢复。
